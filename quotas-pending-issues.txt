## PENDIENTE — ALTA PRIORIDAD

### 1. Formalizar el path M2M interno de Accounts -> SesameFS

Ya está decidida la credencial y ya existe runbook operativo. Lo que falta es cerrar el comportamiento interno del backend para el path máquina-a-máquina.

Pendiente:
- separar internamente cambios manuales de superadmin vs sync M2M de Accounts
- marcar auditoría con `source=accounts`
- registrar actor técnico/credencial de servicio
- agregar idempotencia por `version` o `updated_at`
- rechazar updates viejos o fuera de orden
- dejar trazabilidad clara de provisioning y sync de subscription

Estado actual:
- hoy existen endpoints admin reutilizables
- hoy existe el modelo de API keys endurecido
- hoy existe runbook en `docs/ACCOUNTS-PROVISIONING-RUNBOOK.md`
- falta la formalización del path interno, no la credencial base


### 2. Endpoint preview/evaluate para cambios de plan

Hace falta un endpoint de simulación para que Accounts pueda evaluar el impacto de un downgrade o cambio de plan antes de aplicarlo.

Debe responder, como mínimo:
- si la org quedaría pasada de storage
- si quedaría pasada de tráfico total
- si quedaría pasada de upload traffic
- si quedaría pasada de download traffic
- si quedaría pasada de `max_users`
- cuántos usuarios habría que desactivar
- si los writes quedarían bloqueados

Esto no reemplaza el enforcement real. Es una simulación previa para UX y coordinación con Accounts.


### 3. Flujo de invite/create users vía Accounts

Hoy `AddOrgUser` sigue creando usuarios locales en SesameFS y eso no encaja bien con el modelo donde Accounts gobierna identidad.

Hay que cerrar una de estas rutas:
- invite flow: SesameFS inicia el invite, Accounts crea la identidad, OIDC auto-provision completa el alta
- provisioning flow: Accounts crea/provisiona el usuario y luego llama a SesameFS para reflejarlo localmente

Puntos a resolver:
- quién es source of truth del alta de usuario
- cómo se coordina con `max_users`
- qué queda disponible para owner/org-admin dentro de SesameFS


## PENDIENTE — DECISIONES ABIERTAS CON ACCOUNTS

### 4. Identificador de organización en el contrato externo

Falta decidir si Accounts enviará siempre el `org_id` interno de SesameFS o si hace falta resolver por un identificador externo estable.

Opciones abiertas:
- solo `org_id` interno
- `external_org_id`
- ambos


### 5. Persistencia de IDs externos de billing

Falta decidir si conviene guardar en `organizations` alguno de estos campos:
- `accounts_org_id`
- `subscription_id`

Esto afecta trazabilidad, reconciliación y debugging de syncs externos.


### 6. Snapshot pre-downgrade de usuarios activos

Falta decidir si SesameFS debe guardar qué usuarios estaban activos antes de un downgrade a free para poder reactivarlos automáticamente cuando la org vuelva a paid.

Si no se implementa:
- la reactivación sigue siendo manual por owner/admins

Si se implementa:
- hace falta definir formato, lifecycle y reglas de restauración


## PENDIENTE — UX / OPERACIÓN / OBSERVABILIDAD

### 7. Mensajes de error de quota más específicos

Hoy el frontend todavía no distingue bien entre:
- storage quota exceeded
- traffic quota exceeded
- upload traffic quota exceeded
- download traffic quota exceeded
- max users reached

Hace falta devolver y mostrar errores más accionables.


### 8. Visualización de herencia de quota user -> org

El backend ya soporta herencia cuando el usuario no tiene límite propio. Falta una UI clara para:
- ver cuándo un user hereda de la org
- distinguir override explícito vs herencia


### 9. UI/admin story para traffic quotas

El backend soporta:
- `traffic_quota`
- `traffic_upload_quota`
- `traffic_download_quota`

Falta decidir si el panel sysadmin tendrá:
- edición manual de emergencia
- solo vista de lectura/debug
- o nada, delegando todo a Accounts


### 10. Audit log de quotas y provisioning

Sigue pendiente persistir y exponer trazabilidad de:
- cambios de quota manuales
- provisioning/sync enviados por Accounts
- actor humano vs actor técnico
- source, timestamp y payload mínimo relevante


### 11. Métricas de drops del recorder

Si el recorder se satura y descarta eventos, hoy no hay suficiente visibilidad operativa.

Hace falta:
- contador/métrica de drops
- logging razonable
- visibilidad para detectar pérdida de telemetría de tráfico


### 12. Dashboard de riesgo y notificaciones

No existe todavía:
- vista de riesgo de quotas por org/usuario
- alertas proactivas por cercanía a límites
- notificaciones email/in-app asociadas a quota o downgrade

Esto es útil, pero no forma parte del núcleo ya implementado de enforcement.
