## CONTEXTO NUEVO / DIRECCION ACORDADA (2026-03-26)

- **Accounts será la fuente externa de verdad** para planes, ciclo de billing y límites.
- SesameFS **no debe inferir negocio desde nombres de plan** ni convertirse en el sistema de billing.
- Los cambios de plan y límites llegarán desde Accounts vía **API superadmin**.
- Para esa integración hace falta una autenticación de servicio: idealmente **token de provisioning dedicado**, no una sesión humana de superadmin reciclada.
- Ese token no será solo para quotas: debe poder ejecutar operaciones de aprovisionamiento con alcance de **superadmin técnico** (crear orgs, crear/asignar users, actualizar subscription, etc.).
- `users.role` debe seguir significando **permisos del usuario dentro de su organización**.
- `organizations.plan` debe pasar a significar **identificador opaco del plan externo**. No debe reutilizarse para lógica de permisos.
- El legacy `personalfree`, `business`, `pay_restricted_owner`, `restricted` pertenece a una semántica vieja mezclada entre plan, owner y estado de quota. Eso hay que separarlo.


## HALLAZGOS IMPORTANTES (2026-03-26)

[ ] El "Role" de la lista de organizaciones no es real
        - Backend devuelve `role: "default"` fijo en el listado de orgs
        - Frontend lo muestra como selector editable
        - El endpoint de update de organización no persiste ese campo
        - Conclusión: esa columna induce a error; debe renombrarse a `Plan` o eliminarse

            `personalfree`, `business`, `restricted`, `pay_restricted_owner`
        - Resultado: la capa de UI no tiene un modelo canónico para subscription/plan

[ ] Las organizaciones nuevas no reciben un default free plan consistente
        - Seed, auto-provision OIDC y create organization insertan storage quota por defecto
            pero no fijan `plan`, `billing_cycle`, `traffic_quota`, `traffic_upload_quota`,
            `traffic_download_quota` ni `max_users`
        - El checker actual trata `plan == ""` como free, pero los límites reales pueden quedar abiertos
        - Resultado: una org "nueva" puede ser semánticamente free y operativamente no-free al mismo tiempo

[ ] La lógica de free/pago depende demasiado del nombre textual del plan
        - Hoy `isFree(plan)` devuelve true solo para `""` o `"free"`

## CONCLUSIONES DE ARQUITECTURA (legacy Seafile -> SesameFS robusto)

[ok] El modelo legacy de Seafile mezclaba 4 dimensiones en un solo "role"
    - permisos del usuario
    - plan/comercial del tenant
    - condición especial del owner creador
    - estado de restricción por quota
    - Conclusión: en SesameFS esas dimensiones deben separarse explícitamente

[ok] En SesameFS el `role` debe quedarse solo como autorización
    - `superadmin/admin/user/readonly/guest`
    - Aplica a seguridad, navegación y acciones base del usuario
    - No debe cargar `personalfree`, `business`, `pay_restricted_owner`, etc.

[ok] El `plan` y sus capacidades deben ser org-level
    - El tenant/org es la unidad natural de subscription según docs y esquema multi-tenant
    - Los templates de config y los updates de Accounts deben aterrizar sobre la org
    - El enforcement de quotas/features debe leer el estado efectivo de la org

[ok] El owner creador debe modelarse como condición separada, no como role comercial
    - En Seafile solo el owner entraba en perfiles tipo `personalfree/personalpro/business`
    - Eso sugiere que el concepto real no era un role de seguridad, sino una condición especial del owner frente a billing/subscription
    - En SesameFS eso debería modelarse como `org owner` o capacidad equivalente, separado del `role`

[ok] `restricted`, `pay_restricted` y `pay_restricted_owner` deben migrarse a estado de restricción
    - No como roles
    - Sí como un `restriction_state` o perfil derivado por quota/impago/limitación comercial
    - La excepción del owner se resuelve combinando `restriction_state + owner capability`, no inventando otro role

[ok] El cálculo correcto de capacidades debe ser por capas
    - `role base del user`
    - AND `feature flags del plan/org`
    - AND `restriction state` si aplica
    - AND `owner capabilities` cuando corresponda

[ok] La primera versión no necesita portar todos los flags legacy de Seafile
    - Priorizar flags ya vivos o cercanos:
      `can_add_repo`, `can_share_repo`, `can_add_group`,
      `can_generate_share_link`, `can_generate_upload_link`,
      `can_invite_guest`, `can_send_share_link_mail`, `can_publish_repo`
    - Dejar para más tarde flags de clientes mobile/desktop, rate limits y otros gating legacy menos críticos

[ok] El frontend debe dejar de usar `userRole` como contenedor universal
    - `userRole` debe representar solo permisos del usuario
    - `plan/subscription` debe viajar aparte
    - `restriction_state` y `is_org_owner` también deben ser conceptos separados en responses/UI si hacen falta

[ok] Traducción conceptual del legacy de Seafile al modelo nuevo
    - `default` -> perfil base/template de org, no role de user
    - `guest` -> sigue siendo role de user
    - `personalfree/personalpro/business/pro` -> templates o plan profiles de org
    - `restricted/pay_restricted` -> restriction state
    - `pay_restricted_owner` -> restriction state + owner capability


## PLAN PROPUESTO — MODELO CANONICO ACCOUNTS -> SESAMEFS

### Flujo operativo esperado

1. Usuario crea una cuenta/servicio de cloud storage en Accounts.
2. Accounts aprovisiona la org en SesameFS vía API.
3. SesameFS crea la org con un estado efectivo inicial en DB.
4. Si el usuario hace upgrade, downgrade, deja de pagar o cambia de subscription,
    Accounts envía otro update a SesameFS.
5. SesameFS actualiza la org y la nueva subscription efectiva entra a regir.
6. El superadmin puede seguir haciendo ajustes manuales para personalizaciones,
    incidentes o acuerdos especiales.
7. Si luego Accounts vuelve a sincronizar esa org, **Accounts tiene la última palabra**
    salvo que se defina explícitamente un mecanismo de override persistente.

### 1. Separar definitivamente identidad, permisos y subscription

- **Usuario / permisos**: `users.role`
    - Valores actuales: `superadmin`, `admin`, `user`, `readonly`, `guest`
    - Solo define autorización funcional dentro de la org

- **Organización / subscription**: `organizations.*`
    - `plan`: identificador opaco enviado por Accounts
    - `billing_cycle`: mensual/anual si Accounts lo quiere exponer
    - `storage_quota`, `traffic_quota`, `traffic_upload_quota`, `traffic_download_quota`, `max_users`
    - Hace falta agregar una señal explícita de enforcement, por ejemplo:
        - `quota_policy = hard-stop | soft-overage`
        - o equivalente booleano/enum controlado por Accounts

- **Estado derivado para UX**: respuesta de API al frontend
    - El frontend no debe leer plan desde `role`
    - Debe recibir un objeto o flags de subscription separados, por ejemplo:
        - `plan_code`
        - `is_paid`
        - `quota_policy`
        - `is_over_quota`
        - `can_upgrade`
        - `is_org_owner` si hiciera falta para CTA/banners

### 2. Accounts define catálogo; SesameFS solo materializa y aplica

- El catálogo de 4 planes actuales sirve como contexto, pero **no debe codificarse como enum fijo** en SesameFS
- SesameFS solo necesita:
    - recibir el identificador del plan
    - guardar los límites concretos
    - guardar la política de enforcement
    - aplicar checks técnicos y exponer estado al frontend

- En la práctica:
    - el nombre del plan puede cambiar sin romper enforcement
    - la lógica de free vs pago sale de `quota_policy`, no de comparar strings

### 2.1. Catálogo de planes en archivo de config: sí, pero con un rol acotado

- Tener planes en config **sí puede servir**, pero no como source of truth final.
- Lo correcto sería usar config para uno o más de estos fines:
    - catálogo local de planes conocidos (`free`, `starter`, `business`, etc.)
    - valores por defecto para aprovisionamiento inicial
    - presets reutilizables para asignación manual de orgs desde superadmin
    - validación/normalización de planes conocidos

- Lo que **no** conviene hacer:
    - depender solo del archivo para saber el estado actual de una org
    - impedir que Accounts envíe límites custom que no existan en config
    - recalcular en cada request los límites de la org leyendo el catálogo y olvidando la DB

- Regla recomendada:
    - **Config = catálogo/presets**
    - **DB organization row = estado efectivo actual**
    - **Accounts = última palabra para updates de billing/subscription**

- Esto permite dos cosas a la vez:
    - tener planes estándar definidos localmente
    - soportar personalizaciones por org sin romper el modelo

### 2.2. Overrides manuales del superadmin

- Si el superadmin va a poder personalizar quotas, hay que modelarlo explícitamente.
- Hay 3 opciones razonables:

- **Opción A: override efímero/manual**
    - superadmin cambia límites en la org
    - Accounts puede pisarlos en el próximo sync
    - simple, pero propenso a sorpresas

- **Opción B: override persistente local**
    - la org guarda además un bloque de overrides locales
    - el estado efectivo se calcula como `subscription base + overrides`
    - útil si realmente habrá acuerdos especiales frecuentes

- **Opción C: personalización solo en Accounts**
    - superadmin no edita límites directamente o solo en modo break-glass
    - la personalización real se registra en Accounts y luego se sincroniza hacia SesameFS
    - es el modelo más limpio si Accounts gobierna el billing

- Recomendación actual:
    - si la personalización va a existir de verdad, el modelo más sólido es **base desde Accounts + override local explícito**
    - si será algo raro, mejor **override efímero** con advertencia clara de que Accounts lo puede pisar

### 3. Provisioning inbound desde Accounts

- Recomendado: **endpoint idempotente de provisioning** para updates externos
- Opciones:
    - reutilizar `PUT /api/v2.1/admin/organizations/:org_id/` ampliándolo con auth de servicio
    - o crear un endpoint dedicado tipo `/api/v2.1/admin/provisioning/organizations/:org_id/subscription/`

- Payload mínimo sugerido:
    - `plan`
    - `billing_cycle`
    - `quota_policy`
    - `storage_quota`
    - `traffic_quota`
    - `traffic_upload_quota`
    - `traffic_download_quota`
    - `max_users`
    - `updated_at` o `version`
    - `source = "accounts"`

- Requisitos:
    - idempotencia
    - trazabilidad
    - validación fuerte de límites
    - protección contra updates viejos fuera de orden

### 4. Autenticación para provisioning externo

- **No recomendado**: usar un token de sesión de un humano superadmin
    - expira/rota como sesión humana
    - cuesta auditarlo como integración máquina-a-máquina
    - mezcla identidad personal con identidad de servicio

- **Recomendado**: token dedicado de servicio
    - un solo propósito: provisioning Accounts -> SesameFS
    - con rotación explícita
    - con scope acotado a endpoints de provisioning/admin necesarios
    - con audit log propio

- Importante: este token debe modelarse como una **identidad técnica con privilegios de superadmin para aprovisionamiento**.
    - No significa reutilizar el modelo de sesión de un humano superadmin.
    - Sí significa que puede invocar endpoints equivalentes a tareas de superadmin cuando el caso de uso lo requiera.
    - Ejemplos: crear org, crear usuario owner inicial, actualizar plan/quotas, dar de alta/baja orgs o usuarios si Accounts gobierna ese ciclo.

- Recomendación de diseño:
    - usar un middleware de `service auth` separado
    - fase inicial: tratarlo como `superadmin-equivalent` completo para simplificar
    - fase posterior: si hace falta, endurecerlo con scopes concretos, por ejemplo:
        - `provisioning.organizations.write`
        - `provisioning.users.write`
        - `provisioning.subscriptions.write`
    - o sea: empezar simple, pero sin cerrar la puerta a scopes granulares después

- A nivel de implementación puede entrar como:
    - `Authorization: Bearer <provisioning-token>`
    - o `X-Provisioning-Token: <token>`
    - pero debe validarse en middleware aparte, no como sesión normal de usuario

### 5. Default plan obligatorio al crear org

- Toda org nueva debe nacer con un **default plan explícito** aunque luego Accounts la actualice
- Recomendación inicial:
    - `plan = "free"` o el code canónico que defina Accounts
    - `billing_cycle = "monthly"`
    - `quota_policy = "hard-stop"`
    - límites free completos y explícitos

- Esto debe aplicarse en:
    - seed de default org
    - create organization en admin
    - auto-provision OIDC de orgs nuevas

- Objetivo:
    - evitar orgs "sin plan" ambiguas
    - evitar depender de `plan == ""`
    - asegurar enforcement consistente desde el primer request

### 6. Migración del legacy frontend

- El frontend necesita una migración en dos capas:

- **Capa 1: compatibilidad inmediata**
    - dejar de escribir `app.pageOptions.userRole` con semántica de plan
    - introducir `app.pageOptions.plan` o `subscription`
    - mantener `userRole` solo para permisos

- **Capa 2: limpieza funcional**
    - mover `personalfree`, `business`, `pay_restricted_owner`, `restricted`
        a flags de subscription/estado de quota
    - reescribir `footer-upgrade.js`, `ad.js`, `constants.js` y cualquier CTA equivalente

- `pay_restricted_owner` no debe existir como role
    - semánticamente describe estado de subscription/quota, no permisos del usuario

### 7. Restricciones funcionales para free

- Las restricciones del free deben evaluarse por plan/subscription, no por role
- Role sigue contestando: "¿puede este usuario hacer X por permisos?"
- Plan debe contestar: "¿esta org tiene incluido X?"

- Sitios probables para enforcement adicional por plan:
    - create library
    - create group
    - create share link
    - batch create share links
    - create upload link
    - límites de expiración/link caps en UI y backend

- El orden correcto es:
    1. comprobar auth
    2. comprobar role/permisos
    3. comprobar plan/subscription
    4. comprobar quota/uso actual

[DECIDIDO] Campo canónico para enforcement de negocio

[DECIDIDO] Columna "Role" del listado de organizaciones

[DECIDIDO] Override manual del superadmin vs Accounts

    - No hay overrides persistentes locales

[ISSUE ABIERTO] Sync de roles OIDC vs cambios manuales en SesameFS
    - Decisión operativa actual: transfer de ownership o fixes manuales hechos por superadmin NO deben ser sobreescritos por sync automático de role desde OIDC
    - El mapping de roles OIDC se mantiene, pero la reconciliación fina IdP vs overrides manuales queda como deuda pendiente
    - Requiere diseño específico antes de reactivar cualquier sync agresivo de roles

[DECIDIDO] Endpoints del provisioning token
    - DECISIÓN: Alcance completo superadmin-equivalent en primera versión
    - Reutilizar PUT /admin/organizations/:id/ con service token como auth alternativa
    - Internamente separar M2M path (idempotencia, audit source=accounts) de manual path
    - Refinar scopes después si hace falta

[DECIDIDO] Config de enforcement profiles
    - DECISIÓN: Config organizado por `quota_policy` ("hard"/"soft"), NO por nombre de plan
    - Todos los planes de pago comparten el mismo enforcement profile ("soft")
    - Solo free tiene restricciones de features/límites ("hard")
    - Agregar nuevo plan en Accounts = 0 cambios en SesameFS (solo enviar quota_policy + números)
    - `plan` es string opaco de display, NUNCA se lee para decisiones de lógica de negocio

[DECIDIDO] Dos clases de límites
    - Quotas operativas (storage, traffic, max_users): DB columns, Accounts customiza por org
    - Feature limits (max_libraries, max_share_links, expiry caps): config por quota_policy, NO customizables por org
    - Feature flags (can_add_group, etc.): config por quota_policy, NO customizables por org
    - Si Accounts necesita customizar feature limits por org → migrar a organizations.settings map

[DECIDIDO] Modelo del viejo `pay_restricted_owner`
    - DECISIÓN: No existe en SesameFS. El owner es un role ("owner") en la jerarquía.
    - Owner siempre tiene acceso a admin panel y billing, independiente de quota.
    - Quota enforcement nunca cambia roles ni quita features. Solo bloquea operaciones de datos.
    - `pay_restricted` / `pay_restricted_owner` / `restricted` son código muerto a eliminar del frontend.

[DECIDIDO] Owner de la organización
    - DECISIÓN: Modelar como ROLE (no campo separado). Mismo patrón que grupos.
    - Son 3 dimensiones (role, enforcement profile, quota state), NO 4.
    - Owner es un nivel de autorización privilegiado que incluye billing responsibility.
    - Jerarquía: superadmin(5) > owner(4) > admin(3) > user(2) > readonly(1) > guest(0)
    - Owner puede: ver billing, iniciar upgrade, transferir ownership, eliminar/deactivar org
    - Transfer: swap roles (old owner→admin, new→owner). Solo 1 owner por org.
    - Creador de la org = role owner (no admin como antes)
    - Si en el futuro se necesita co-owner o billing-viewer, se extrae a campo separado

[DECIDIDO] Features limitadas en free
    - DECISIÓN: Matriz completa definida. Ver docs/PLANS-AND-PERMISSIONS.md
    - Free NO puede: crear grupos, invitar guests, publish repo, send share link mail, global address book
    - Free SÍ puede (con límites): crear repos (max 3), share links (max 3, 3 días), upload links (max 1, 3 días)
    - Free SÍ puede: conectar clientes desktop/mobile
    - Quotas free: 2GB storage, 10GB tráfico/mes combinado, 1 user max

[DECIDIDO] Paid plan enforcement
    - DECISIÓN: Soft warning confirmado. Paid = soft, uploads/downloads PASAN con warning.
    - max_users es siempre hard block (si existe límite explícito)
    - Billing en Accounts se encarga de cobrar overage

[DECIDIDO] Planes disponibles
        - DECISIÓN: En SesameFS hay 2 enforcement profiles canónicos: `hard` y `soft`.
        - `hard` = comportamiento free; `soft` = comportamiento paid.
        - El nombre del plan es un display string opaco enviado por Accounts y NO se usa para lógica.
        - Puede haber muchos nombres comerciales de planes pagados (`Starter`, `Business`, etc.)
            mapeando al mismo enforcement profile `soft`.
        - Org base de la plataforma (seed) = profile `soft` con cuotas ilimitadas por defecto.

[DECIDIDO] Tráfico free
    - DECISIÓN: 10GB combinado sin sub-límites upload/download
    - traffic_quota = 10GB, traffic_upload_quota = -1, traffic_download_quota = -1
    - Planes de pago sí tienen sub-límites separados (Accounts los fija)
        - El contrato API debe contemplar tanto tráfico combinado como upload/download por separado
            para warnings y enforcement granular cuando existan sub-límites
        - El enforcement de tráfico no debe basarse en mes natural sino en `current_period_started_at`
            + `current_period_ends_at` de la org
        - `current_period_ends_at` es la referencia canónica para saber si el período venció
        - Accounts puede mandar `current_period_ends_at`; si no lo manda, SesameFS lo deriva
            desde `current_period_started_at` con la fórmula mensual estándar tipo Stripe
        - Hace falta una agregación optimizada por período efectivo de la org
            para no depender del mes natural ni recalcular desde cero en cada request
        - Hace falta un job periódico de rollover del período actual para cualquier org vencida,
            no solo free; puede vivir junto al scheduler del GC si conviene operativamente
        - Ese job debe seleccionar por `current_period_ends_at <= now` y avanzar múltiples períodos
            si la org quedó atrasada por downtime o retrasos
        - No hay que limpiar histórico: solo avanzar el período efectivo

[DECIDIDO] Contrato backend → frontend
    - DECISIÓN: Backend envía estado pre-digerido, frontend no hace cálculos de negocio
    - `storage: {used, quota, percent, over_quota}` — objeto pre-calculado
        - Storage no tiene períodos: o está dentro del límite o se bloquean writes
        - `traffic: {used, quota, percent, over_quota, upload_used, upload_quota,
            upload_over_quota, download_used, download_quota, download_over_quota, reset_date}`
            — objeto pre-calculado
        - `current_period_started_at` + `current_period_ends_at` deben viajar aparte como
            source of truth del período vigente; `reset_date` se deriva de ahí
    - `upgrade_features: [...]` — lista de features bloqueadas por plan (no por role)
    - `can_upgrade: true/false` — pre-calculado por backend, frontend solo lo muestra
    - El frontend NUNCA compara plan names ni compara role contra features
    - Ver docs/PLANS-AND-PERMISSIONS.md sección "Frontend Contract"

[DECIDIDO] `can_upgrade` para owners
    - DECISIÓN: `can_upgrade=true` para CUALQUIER owner cuando hay razón para upgrade
    - Free owner → siempre true (upgrade a paid)
    - Paid owner con storage o traffic >= 80% → true (upgrade a más capacidad)
    - Paid owner con storage o traffic over_quota → true
    - Paid owner con uso holgado → false (no hay razón para CTA)
    - Non-owner → siempre false (solo info, "contact your admin")

[DECIDIDO] UX de features bloqueadas por plan
    - DECISIÓN: Frontend muestra la feature como disabled/locked con badge de upgrade
    - Backend envía `upgrade_features` list — frontend lee directamente sin lógica de negocio
    - Owner: "Upgrade to unlock" + botón de upgrade
    - Non-owner: "Contact your admin" o solo locked icon

[DECIDIDO] Lifecycle comercial (impago, suspensión, downgrade)
    - DECISIÓN: Por ahora impago = Accounts envía status=deactivated. Todo bloqueado.
        - Grace period lo maneja Accounts externamente y dura 1 mes desde el vencimiento.
        - Si ese período expira sin pago, Accounts aplica el cambio correspondiente.
        - Downgrade paid -> free: Accounts envía `quota_policy=hard` + cuotas free.
        - Si la org downgraded queda pasada de tráfico:
            se bloquean las operaciones afectadas por traffic quota hasta el próximo período.
        - Si la org downgraded queda pasada de max_users:
            pueden desactivarse usuarios regulares, pero se mantienen activos owner y admins.
        - La API de org-admin no debe permitir reactivar users si eso vuelve a exceder el límite efectivo.
        - El superadmin no queda sujeto a esa restricción operativa.
        - Si la org downgraded queda pasada de storage:
            no se permite subir más contenido; todos los writes quedan bloqueados.
        - En downgrade no se borran datos existentes.
        - Lecturas/descargas existentes se preservan salvo que otro enforcement específico lo bloquee.
        - Si luego la org vuelve a un plan pago, la reactivación de usuarios no es automática:
            owner y admins deciden a quién reactivar manualmente.
    - Si se necesitan estados intermedios ("past_due" = lectura sí, escritura no), agregar
      `billing_status` a organizations. Explícitamente diferido hasta que Accounts lo requiera.

[DECIDIDO] Endpoint de preview/evaluate para cambios de plan
        - DECISIÓN: Sí conviene tenerlo desde temprano.
        - Sirve para que Accounts evalúe el impacto de un downgrade o cambio de plan antes de aplicarlo.
        - Debe permitir detectar si la org quedaría pasada de storage, tráfico combinado,
            upload traffic, download traffic o max_users.
        - La simulación debe evaluar contra el período vigente/propuesto de la org,
            no contra el mes natural UTC.
        - También puede devolver warnings/impactos derivados, por ejemplo writes bloqueados
            o cantidad estimada de users a desactivar.
        - No reemplaza el enforcement real; es una capacidad de simulación previa.
